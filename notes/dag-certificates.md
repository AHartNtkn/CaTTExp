# Sharing-aware certificates for large CaTT terms

*Thread "Build a sharing-aware Agda checker" (DAGC), 2026-11-25. Code: `src/CaTTExp/Dag/`, `tools/dag_cert.py`, `tools/gen_dag_trie.py`. Open-issues row G6.*

## Problem

The certified checker (`certified?`, `==Tm`, checking by `refl`) walks terms as trees. Answers produced by the relative-coherence descent share subterms heavily: the answer to Horiz3 query (2) (cone over the horizontal 3-globe composite) has about 2.6·10¹¹ nodes as a tree but only 0.74M distinct subterms. No tree-walking check can finish on it, so the answer had no Agda certificate.

## Design

A certificate is a table of items in one id space, topologically sorted (every reference points to a smaller id):

| item | meaning |
|---|---|
| `V i` | the variable of level i (ids 0..K−1 are exactly `V 0 … V (K−1)`, checked) |
| `C h as` | `coh` with head h applied to the argument ids `as` (last argument first) |
| `E`, `S c A` | the empty context, and context c extended by type A |
| `H c A` | a coherence head: pasting context c, type A |

Types `RTy` are lists of (source, target) id pairs. Unfolding (`Dag.Unfold`) maps ids to ordinary syntax (`⟦ n ⟧`, `⟦ c ⟧c`, `⟦ A ⟧ty`). It takes fuel, and on a decreasing table the result does not depend on the fuel (`Irr`), so the unfolding equations hold (`⟦⟧-C` and friends).

The certificate also carries **untrusted claims**: typing claims J(c, n) = A ("in context c, term n has type A"), and free-variable claims F(n) (the sorted variable levels of n and of its type). Each item and each claim is checked once, **locally** (`Dag.Check`):

- a variable claim is checked against the context's entry;
- a coherence claim checks the argument claims against the head's context instantiated by the substitution (instantiation of head types is by ids, memoized within one claim), the head (pasting context by `checkPs`, the type well formed, the side condition from the F claims), and that the claimed type is the instantiated head type;
- F claims are checked from the F claims of the subterms (a merge of sorted lists).

No check unfolds the terms of the answer: the only unfoldings are of head contexts (pasting contexts, for `checkPs` and the side condition) and, for `certified`, of the root's context and type for the comparison with the query. Equality of terms is equality of ids; the generator hash-conses, so this is complete for its output, and soundness never depends on it.

**Soundness** (`Dag.Sound`): if every item and claim passes, then every claim is a real derivation of the unfolded judgment, `⟦ c ⟧c ⊢tm ⟦ n ⟧ ∶ ⟦ A ⟧ty` (induction on ids, with the semantic invariants `SemJ`, `SemC`, `SemH`). The decoder, the tries and the claims are untrusted for the certificate's own tables: the theorem holds for whatever tables they produce.

**The query.** For queries small enough to write in ordinary syntax, the certificate's root is compared with the query by `==Ctx`/`==Ty` (`certified`). Large queries are trees too: Horiz3 query (2)'s type unfolds to millions of nodes, and comparing it as a tree was what ran out of memory. So the query is given as its own hash-consed table (2,700 items for Horiz3 query (2)) and compared with the certificate's root by ids, with a memo of pairs already shown equal (`Dag.QEq`, sound for decreasing tables). The statement proved is

```agda
certifiedQ : runCertQ K is cs fs qs g n A qg qA ≡ true →
             Σ Tm (λ w → queryCtxOf qs qg ⊢tm w ∶ queryTyOf qs qA)
```

where `queryCtxOf`/`queryTyOf` unfold the query table. **For `certifiedQ` the query decoder is trusted for meaning**: the derivation is real for whatever query the strings decode and unfold to (`nums`, `natmap`, `unpack`, `parseI`, `rty`, `Unfold`), so "this is the intended query" rests on those definitions and on `dag_cert.emit_qtable`. For small queries, `queryMatches` checks (by `refl`) that the query table unfolds to the query in ordinary syntax, which closes the gap (`DagSmallCheck.answer′`). For Horiz3 query (2) the query is specified by the Python fixture `tools/fixtures/rc_horiz3_query2.txt.gz` plus `emit_qtable` plus the decoder; nothing in Agda yet ties it to an Agda-side statement of the cone over the horizontal 3-globe composite.

## Running it

`tools/dag_cert.py` builds the certificate from a context, type and term (`emit_all(prefix, G, A, w, outdir)`) and writes `<prefix>Data.agda` (the tables as base-32 strings), `<prefix>QTable.agda` (the query table) and `<prefix>Check.agda` (`accepted = refl` and `answer`).

Performance notes (Agda 2.7.0.1, evaluation of `refl`):

- Agda does not memoize top-level definitions, so the decoded tables are passed as arguments, never named at top level inside the checks.
- Tables are 4-ary tries (`Dag.Trie`, generated by `tools/gen_dag_trie.py`), built with `primForce` so that no thunk keeps earlier versions alive.
- Argument lists, claimed types and free-variable lists are stored packed into one number each (`Run.unpack`); a list costs tens of machine words per element in the evaluator.

| test | items | claims | time | max residency |
|---|---|---|---|---|
| `DagSmallCheck` (with tree comparison of the query) | 631 | 716 | 28 s | small |
| `DagMidCheck` (subterm of the Horiz3 answer) | 18,794 | 19,036 | 75 s | 150 MB |
| `DagHoriz3Q2Check` (the whole answer) | 779,079 | 824,300 | 73.5 min | 1.34 GB (3.6 GB in use) |

## Status

**The Horiz3 query (2) fixture answer is certified in Agda** (2026-11-25), as a test at scale. It is not part of the Horiz3 cone: the cone thread reports that the cone construction never asks this fixture literally (the round-21 cap sweep needs a sub-query with the same context but different A, t, u). Details: `DagHoriz3Q2Check` (`accepted = refl`, `answer = certifiedQ …`) type-checks with Agda 2.7.0.1 under `--safe`, in 73.5 min with a 1.34 GB maximum residency (`+RTS -M12G`), from the interfaces of the data modules. Checking the 82 MB data module itself took 6 GB of residency; `dag_cert.py` now splits large data into part modules. The generated modules (not in git) are in the project files under `dag-certs/` and are rebuilt by `tools/dag_horiz3_q2.py`. As said above, the query is the one specified by the Python fixture and the query-table decoder.

**The whole Horiz3 cone context is certified well formed** (2026-11-26). This is the 31-entry cone over `ConeShapesThree.Horiz3`, computed by `tools/cone_rcs.py` (the cone thread's sharing-preserving Python mirror of `ConeRCS`) from the 25-entry answer table. It is one certificate: 1,131,869 items, 1,188,413 claims, 11.9M argument slots. The 25 answers share a lot: 1.09M distinct subterms together, against 1.51M if counted separately. `DagHoriz3ConeCheck` proves `queryCtxOf queryS qCtx ⊢ctx` (`Dag.Sound.certifiedCtxQ`, a context given as a table). It type-checks by `refl` under `--safe` in 130 min, with 6.3 GB maximum residency and 12 GB in use (`+RTS -M12G`), counting the checking of its 150 MB of data and query modules. A whole-context check in the Python kernel did not finish in 2 h. The modules are in the project files under `dag-certs/horiz3-cone/`. `tools/dag_horiz3_cone.py` rebuilds them with the same content, but it now splits the 63 MB query table into part modules as well; the timing above was measured with the query table in one module. The input is the pickled context `horiz3-cone-ctx.pkl` in the cone thread's project files, which `tools/cone_rcs.py` computes (merged in #636). The small test `DagCtxSmallCheck` (3,567 items: an answer's context extended by its query type) is committed, and a wrong context of the same shape is rejected.

What this does not yet show: that this context is what the Agda construction `ConeRCS (TBL orRC rc1) Horiz3` returns. The link is the Python mirror, which the cone thread checked against the 25 queries of the Agda construction. Evaluating `ConeRCS` in Agda does not scale, because `Cones` walks unshared trees (85 min per query by round 24). Also as above, the context is the one the query-table decoder makes of `queryS`.

Open items are in the G6 row of `open-issues.md`.
